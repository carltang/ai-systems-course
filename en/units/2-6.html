Explanation

  1. 1autocast: one more stop on the way of each operator call, choosing the precision by the kind of operator

    With automatic mixed precision on, every operator call passes through an "autocast" stop before reaching the backend. This stop looks up a list: operators like matrix multiplication and convolution have their inputs converted to 16 bits before computing; precision-sensitive operators like sums, exponentials and loss functions have their inputs converted back to 32 bits; all other operators keep their inputs' original type.

    1.5 explained why low precision is used: matrix multiplications can use Tensor Cores, and memory reads and writes are halved. Here we see how it is implemented in the framework.

    It is a stop on the dispatcher. As 2.3 explained, an operator call passes through several "features" in order of priority. Inside with torch.autocast(device_type="cuda", dtype=torch.bfloat16): the current thread has one more dispatch key switched on. So every call's route becomes: autograd → autocast → CUDA backend.

    What this stop does. It divides operators into three kinds:

    • Converted to 16 bits. Matrix multiplications, linear layers, convolutions, attention: heavy on arithmetic and not very sensitive to precision. autocast converts the inputs to 16 bits, then dispatches on.
    • Converted to 32 bits. Those sensitive to the range of values or to rounding error: exponentials and logarithms, powers, large sums, some steps inside normalisation, the various loss functions. Even if the inputs are 16-bit, they are converted to 32 bits before computing.
    • Left alone. All other operators compute in whatever type their inputs have. If several inputs have different types, the widest wins.

    The full lists are on the Automatic Mixed Precision page of the official documentation.

    The parameters themselves stay in 32 bits. autocast does not change the type of the model's parameters. A linear layer's weights are stored in 32 bits and converted into a temporary 16-bit copy for computation at each forward pass. In the backward pass the gradients flow back to the 32-bit weights, and the optimizer updates in 32 bits. Among the "16 bytes" of 7.2, the 2 bytes of 16-bit parameters and the 4 bytes of the 32-bit master copy are these two copies.

    The backward pass need not be inside autocast. The precision each operator used in the forward pass is already recorded in its backward node; in the backward pass each node computes in the precision of its forward operator. So wrap only the forward pass and the loss computation, and put loss.backward() outside.

    Choosing between bf16 and fp16. Both are 16 bits, divided differently (1.5). bf16 covers the same range of values as 32 bits, rarely overflows, is supported by newer GPUs, and is the first choice today; fp16 has a small range and needs the loss scaling of the next card to keep gradients from underflowing.

    Troubleshooting numerical problems. If the loss becomes NaN after turning on mixed precision, first confirm it is the cause (turn it off and run again). If it is, a common reason is some operation you wrote yourself overflowing in 16 bits, such as squaring or exponentiating a large number. Put that small part back in 32 bits on its own:

    with torch.autocast(device_type="cuda", enabled=False):
    y = risky_op(x.float())

    An analogyLike sorting at a factory's inspection point: high-volume standard parts go down the fast lane (16 bits), precision parts down the slow, careful lane (32 bits). The sorting rules are fixed in advance by the kind of part, so workers need not judge each piece.

    So using mixed precision needs no change to model code, just the forward pass wrapped in autocast. But for the same reason, which operations actually run in 16 bits is decided by this list; if a special operation of your own is sensitive to precision, put it back in 32 bits yourself.

  2. Computing in 16 bits narrows the range of values. For one of the 16-bit formats, this causes a specific problem.

  3. 2fp16 needs loss scaling; bf16 usually does not

    fp16 has few exponent bits, so the smallest number it can represent is limited, and many very small gradients simply become 0 (underflow). Loss scaling first multiplies the loss by a large number so the gradients land within fp16's range, then divides them back before updating the parameters. bf16 has the same range as fp32 and generally does not need this step.

    The problem: gradient underflow. The smallest positive number fp16 can represent is of the order of 6×10⁻⁸ (anything smaller can only be represented as 0). Many gradients in training are smaller than that, especially in the layers near the input. In fp16 they simply become 0, and the corresponding parameters get no update. This error is silent: nothing fails; training just gets worse.

    The cure: scale everything up, then back down afterwards. Gradients are derivatives of the loss. Multiply the loss by a large number S (say 65536), and by the chain rule every gradient in the backward pass is S times larger; small gradients that would have underflowed now fall within fp16's range. When it is time to update the parameters, divide the gradients by S to restore their real size (done in 32 bits, where nothing underflows).

    How large S should be. Too small is not enough; too large amplifies gradients that were already large until they overflow to infinity. PyTorch's GradScaler adjusts it dynamically:

    • Each step it checks whether the gradients contain infinity or NaN.
    • If so: S is too large. Skip this step's parameter update and halve S.
    • If none for many steps in a row: raise S a little.

    So the usage is always the same three lines: scaler.scale(loss).backward(), scaler.step(optimizer), scaler.update().

    Why bf16 does not need it. 1.5 explained the difference between the two 16-bit formats: fp16 gives more bits to the fraction and has a small exponent range; bf16 has as many exponent bits as 32-bit floating point, hence the same range of values, only fewer significant digits. With the same range, there is no problem of "gradients that were fine in 32 bits underflowing to 0 in 16".

    So on GPUs that support bf16 (the A100 and the generations after it), use bf16 directly, with no GradScaler: simpler code and one less thing to go wrong.

    Troubleshooting. When training in fp16, if the loss becomes NaN or stops falling for a long time: first look at the scaler's factor (scaler.get_scale()). If it keeps shrinking, gradients keep overflowing, and the model may have a numerically unstable spot; if it is stable at some value, the problem is probably not the scaling.

    An analogyLike weighing something very light on a scale with a coarse range: weigh it multiplied a thousandfold, then divide the reading back.

    So on GPUs with bf16, prefer bf16 and skip the trouble of GradScaler; when training in fp16, if the loss becomes NaN or will not fall, check the scaling first.

  4. Forward and backward are taken care of. One stretch of the training step remains: the optimizer updating the parameters. It looks trivial, yet sometimes takes a sizeable share.

  5. 3The optimizer can be slow too: hundreds of small kernels lose to a few large ones

    A naive optimizer updates one parameter tensor at a time; a model with hundreds of tensors means hundreds of small kernel launches, each doing a little work. The foreach version processes tensors of a kind in batches, and the fused version merges the whole update into one kernel.

    The most direct way. A model's parameters are many tensors: each layer's weights and biases, the normalisation coefficients. The optimizer applies the update formula to each tensor separately. One Adam update is about a dozen element-wise operators (update the first moment, the second moment, correct the bias, compute the step, change the parameter). Hundreds of parameter tensors make thousands of operator calls.

    Each walks the path of 2.3 and pays a fixed cost; and many parameter tensors are small (biases and normalisation coefficients have a few hundred or thousand elements), taking a few microseconds on the GPU. This is exactly "overhead-bound": the time goes into giving orders.

    foreach: gather operations of the same kind. PyTorch provides a set of operators that take "lists of tensors". Instead of calling addition once for each parameter tensor, the optimizer puts all parameter tensors in a list and calls "add each pair in the lists" once. Python and dispatcher overhead drops from "once per tensor per operator" to "once per operator". On the GPU there are still many small kernels, but the orders go out much faster.

    fused: one kernel for the whole update. Go further and write Adam's dozen steps into one CUDA kernel: for each element, read the parameter, the gradient and the two pieces of state in one go, compute all the steps, and write back. This saves two things at once: the number of orders, and the memory reads and writes of intermediate results (a dozen operators each reading and writing becomes one read and write in all). This is the fusion of 4.2, only written by hand here.

    ImplementationOperator callsIntermediate results
    for-loopNumber of parameter tensors × steps per updateWritten out at every step
    foreachSteps per updateWritten out at every step
    fusedAbout 1Never written out

    How to use it. Newer PyTorch uses foreach by default on the GPU. fused has to be turned on explicitly: torch.optim.AdamW(params, lr=..., fused=True). Karpathy does exactly this in the GPT-2 reproduction video (1.5).

    How much it gains. It depends on how much of the total time the optimizer step takes. Models with many small parameter tensors (many layers, none large) gain clearly; models whose parameters sit in a few large matrices spend little time in the optimizer anyway. The timestamps of 0.2 tell you directly what percentage the "optimizer" stretch takes.

    This is "batching to spread fixed costs" from 0.1, applied to the optimizer.

    An analogyLike sending parcels: a hundred small packages sent a hundred times lose to one big box sent once.

    So with many parameter tensors, the optimizer step can be dominated by launch overhead; switching to the foreach or fused implementation is a speed-up at almost no cost.

  6. Every cure so far has been "make the same computation run faster". The last line of thought is different: make the computation smaller.

  7. 4The fastest computation is the one you do not do

    Pruning removes unimportant weights, compression makes the model smaller, distillation has a small model learn from a large one. But note: zeroing scattered weights (unstructured sparsity) usually does not make the GPU any faster; only removing them by block or by channel, or a sparse format the hardware supports, really reduces the computation.

    Some ways of "making it smaller".

    • Pruning: remove unimportant weights (set them to zero).
    • Distillation: train a small model to imitate a large model's outputs.
    • Low-rank factorisation: approximate a large matrix by the product of two small ones.
    • Quantisation: represent each number with fewer bits (covered in 9.2).

    The key judgement: does it reduce the number of parameters, or the actual computation and reads and writes? The two are not the same.

    Take pruning. Set 90% of a weight matrix's elements to zero, scattered (unstructured pruning), and the "effective number" of parameters drops tenfold. But the matrix is as large as before, and so is its storage; the matrix multiplication kernel still does a multiply-add for every element, nine in ten of them multiplying by zero. Not a moment is saved on the GPU.

    To really save, the zeros must come "in whole pieces":

    • Structured pruning: remove whole rows, columns, attention heads or layers. Afterwards the matrices really are smaller, and computation and reads and writes fall with them.
    • A sparse format the hardware supports: the Tensor Cores of some GPUs support one fixed pattern of sparsity (keep 2 of every 4 elements), which with dedicated libraries gives real speed-ups.

    Why is scattered sparsity hard to exploit on a GPU? Because a GPU relies on regularity: a group of threads does the same operation on a contiguous block of data at once (part 3). A sparse matrix has to be accessed in jumps by index, memory accesses cannot coalesce, and the work is uneven between threads; unless it is so sparse that only a few percent remain, computing it densely is better.

    Test any "simplification" in the language of part 0. Ask three things:

    • Are there fewer floating-point operations? (compute)
    • Are fewer bytes read from and written to GPU memory? (bandwidth)
    • Are there fewer kernels? (overhead)

    If none of the three changed, the speed will not change, however many fewer parameters there are. A distilled small model has less of all three, so it really is faster; quantisation mainly reduces the second (9.2); low-rank factorisation replaces one large matrix multiplication with two small ones, so the first two fall and the third rises a little.

    These methods are usually used for deploying inference rather than speeding up training: most of them need a trained model first. They are in this unit to complete the list of speed-ups, and to give the standard for judging them.

    An analogyLike streamlining a procedure: deleting a step saves time; crossing out a few words in each step leaves the procedure just as long.

    So to evaluate a way of "simplifying the model", look at whether it reduces real computation and reads and writes on the GPU, not just the number of parameters.

Putting it together

autocast is a stop on the way of each operator call, choosing the precision by the kind of operator; the parameters are still kept in 32 bits. fp16 needs loss scaling to keep gradients from underflowing; bf16 usually does not. Optimizers updating tensor by tensor are dragged down by launch overhead, and the foreach and fused versions combine them. Simplifying the model only makes it faster when it really reduces computation and reads and writes.
