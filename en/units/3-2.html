Part 3 · The GPU and the CUDA execution model3.2 The first CUDA kernel

Translated by AI (Anthropic's Claude) from the Chinese edition. The Chinese original is the reference.

This unit answersHow do thousands of threads each find their own share of the work?
Follows 3.1: the GPU's strength is doing a great deal of identical work at once; this unit is about handing that work out to threads.

The previous unit said the GPU is good at "doing a great deal of identical work at once". This unit answers: how exactly is the work handed out? The thread: write the code for one thread only → each thread finds its data by its number → the data first has to be moved from the CPU to the GPU → threads are grouped into blocks, and blocks do not depend on each other.

  1. Write the code for one thread, and run a million copies of it
  2. A thread's address: blockIdx × blockDim + threadIdx
  3. The CPU and the GPU each have their own memory, with a narrow road between
  4. Blocks never wait for each other, so the same program runs on large and small GPUs alike

Explanation

  1. 1Write the code for one thread, and run a million copies of it

    A CUDA kernel describes "what one thread does". When launching the kernel you say how many threads to start; all threads run the same code, each on different data. This is called SPMD (single program, multiple data). Parallelism is not written; it is "launched".

    To add the elements of two arrays on the CPU, you write a loop:

    for (int i = 0; i < n; i++) c[i] = a[i] + b[i];

    In CUDA the loop disappears. You write only the body of the loop, that is, "how element i is computed":

    __global__ void add(float* a, float* b, float* c, int n) {
    int i = /* which thread am I */;
    if (i < n) c[i] = a[i] + b[i];
}

    Then at launch you say "start n threads to run it". The n threads run this same code at once, each with a different i.

    This is SPMD (single program, multiple data): one program, many pieces of data. It corresponds directly to the previous unit's conclusion: the GPU is good at large amounts of identical work, and a kernel is the description of "the identical work".

    So the first step in moving CPU code to the GPU is always to find the loop whose "iterations do not depend on each other": the loop variable becomes the thread number, and the loop body becomes the kernel. If the iterations depend on each other (step i needs the result of step i−1, say), you cannot do this directly; that is the subject of 3.5.

    An analogyLike handing a million workers the same job sheet: everyone follows the same sheet and uses their own staff number to collect different materials.

    So the way to write a kernel is: first be clear "how one element is computed", then "which thread handles which element". A loop in CPU code often becomes threads.

  2. Every thread runs the same code, so how does it know which element it should handle? By its number.

  3. 2A thread's address: blockIdx × blockDim + threadIdx

    Threads are organised in two levels: a grid is made of thread blocks, and a block is made of threads. A thread's global number = block number × threads per block + number within the block, and it uses this to find the data it is responsible for. To round up, more threads are usually started than there is data, and the extra ones must be stopped with if (i < n).

    Threads are not one flat list but two levels: some threads make a block, some blocks make the grid. Each thread can read three built-in variables: blockIdx (which block I am in), blockDim (how many threads each block has) and threadIdx (my place within the block).

    The global number is: i = blockIdx.x * blockDim.x + threadIdx.x. With 256 threads per block, for example, thread 10 in block 3 has global number 3 × 256 + 10 = 778, and is responsible for c[778].

    Why check the bounds? Because threads can only be started a whole block at a time. With 1000 elements and 256 threads per block, you start ⌈1000/256⌉ = 4 blocks, 1024 threads in all. The 24 threads numbered 1000 to 1023 have no data; if they are not stopped, they read and write memory past the end of the arrays that does not belong to you.

    The two-dimensional case (images, matrices) is exactly the same, just computed once for each of the x and y directions: the column number from the three x variables, the row number from the three y variables.

    Example: processing a 1920×1080 image, how large should the grid be?

    Suppose each block has 16×16 = 256 threads and each thread handles one pixel.

    • x direction (width 1920): 1920 ÷ 16 = 120, exactly 120 blocks.
    • y direction (height 1080): 1080 ÷ 16 = 67.5, rounded up to 68 blocks.

    So the grid is 120×68, 8160 blocks in all, about 2.09 million threads. The threads cover 1920×1088, 8 rows more than the image (15360 threads), and these threads must be stopped by the bounds check.

    In the kernel each thread finds its pixel like this:

    int col = blockIdx.x * blockDim.x + threadIdx.x;
int row = blockIdx.y * blockDim.y + threadIdx.y;
if (col < width && row < height) {
    int i = row * width + col;       // the image is stored by rows: row `row`, column `col`
    out[i] = /* compute the result from in[i] */;
}

    A common way to round up: (n + blockSize - 1) / blockSize, which gives ⌈n / blockSize⌉ with integer division.

    An analogyLike working out an estate-wide flat number as "building number × flats per building + flat number"; the last building is not full, and you must not knock on the empty flats' doors.

    So the first line of almost every kernel computes an index and the second checks bounds; for two-dimensional data such as images and matrices, the column and row are computed separately in the x and y directions.

  4. A thread has found its position, but where is the data it is to process? At first it is in memory on the CPU side, which the GPU cannot reach.

  5. 3The CPU and the GPU each have their own memory, with a narrow road between

    Host memory and GPU memory are separate, and data has to be copied across PCIe. GPU memory bandwidth is of the order of a thousand GB per second; PCIe only tens of GB per second, a few dozen times less.

    The memory the CPU uses (host memory) and the memory the GPU uses (GPU memory) are two separate stores, connected by the PCIe bus. Kernels on the GPU can only read and write GPU memory, so data must be copied over first, and results copied back when needed.

    The trouble is that this channel is narrow. The GPU reads and writes its own memory at hundreds to over a thousand GB per second; PCIe transfers at roughly ten to a few dozen GB per second. Copying 1 GB of data takes tens of milliseconds, while one element-wise operation on 1 GB of data takes the GPU a few milliseconds. In other words, the time to move the data once is enough to compute ten times.

    That gives a practical rule: once data is on the GPU, do not let it out lightly. Do a long chain of operations on the GPU in one go, and copy back only the results you need at the end.

    The most common trap in a training loop is calling loss.item() or .cpu() at every step. They not only trigger a copy but also make the CPU stop and wait for the GPU to finish every earlier task (because the GPU is asynchronous; see 3.1). Printing once in a while is fine; doing it every step slows things down noticeably.

    An analogyInside the factory (the GPU) things move fast, but the raw-materials warehouse (CPU memory) is outside town, with only a small road between.

    So keep data on the GPU as much as possible and do many steps of computation there in a row; copying back and forth between CPU and GPU often takes longer than the computation itself. In PyTorch, .cpu() and .item() both trigger a copy and a synchronisation.

  6. Back to the two levels of threads: why divide them into blocks rather than one big plane? Because a block is a boundary: inside it threads can cooperate, across it they have nothing to do with each other.

  7. 4Blocks never wait for each other, so the same program runs on large and small GPUs alike

    Threads in the same block can synchronise with __syncthreads() and share shared memory; different blocks have no guarantee of execution order and are independent of each other. The hardware can schedule them in any order, with any degree of parallelism.

    Threads in the same block have two privileges: they share a small piece of very fast storage (shared memory), and they can wait for each other with __syncthreads(), meaning "once everyone has reached this point, go on together". This lets them cooperate on one job, for instance moving a block of data into shared memory together and then each using it (the tiling of 3.3).

    Between different blocks there is no guarantee at all: which runs first, which later, or whether they run at the same time is up to the hardware, and the program may not assume anything.

    What this restriction buys is scalability. Because blocks do not depend on each other, the hardware is free to arrange them: on a small GPU 8 blocks run at once and the rest queue; on a large GPU 100 run at once. Without changing a single character of the program, performance grows with the hardware automatically. This is called transparent scalability.

    The other way round, it constrains how you design algorithms: work that needs threads to cooperate closely must be placed within one block; cooperation across blocks can only be achieved by "launching one kernel to finish, then launching the next".

    An analogyLike an exam held in several rooms: within a room an invigilator gives everyone the same instructions; the rooms have nothing to do with each other; with many rooms everyone sits the exam at once, with few they sit it in turns.

    So the same kernel runs faster automatically on a large GPU with more SMs (transparent scalability); it also means you cannot write logic that depends on "another block finishing first".

Putting it together

Because a kernel describes the work of one thread, the key is the conversion from a thread's number to a position in the data; because moving data between the two memories is expensive, keep the data on the GPU; because blocks are independent of each other, the same program runs on a GPU of any size.
