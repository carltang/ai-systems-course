Part 3 · The GPU and the CUDA execution model3.6 Streams, asynchrony and CUDA Graphs

Translated by AI (Anthropic's Claude) from the Chinese edition. The Chinese original is the reference.

This unit answersHow does the "chain of command" from the CPU to the GPU work? How can the overhead of giving orders be reduced?
Follows "synchronise before timing" in 3.1: there we only said the GPU is asynchronous; this unit explains how far the asynchrony goes.

The thread: between the CPU and the GPU sits a task queue, which is where the asynchrony comes from → there can be more than one queue, each called a stream, and streams can run concurrently → some operations force the CPU to stop and wait for the queue to empty, and these synchronisation points often hide in inconspicuous code → the overhead of giving orders itself can be pressed to a minimum by "recording once and replaying" → finally, what happens when several processes share one GPU. Many earlier units used these mechanisms (asynchronous copies, DDP's overlap, the low-overhead mode of compilation); here their common foundation is made clear.

  1. A queue sits between the CPU and the GPU: issuing a task is not finishing it
  2. Streams: in order within one queue, at the same time across different queues
  3. Synchronisation points: whenever the CPU needs an actual value from the GPU, it must stop and wait
  4. CUDA Graphs: record the launches of a string of kernels, and replay them in one go afterwards
  5. Several processes sharing one GPU: they take turns by default, not run at the same time

Explanation

  1. 1A queue sits between the CPU and the GPU: issuing a task is not finishing it

    When a program on the CPU calls CUDA to launch a kernel or a copy, all it really does is put the task on the GPU's queue and return at once. The GPU takes tasks from the queue in order and executes them. The CPU and the GPU each get on with their own work, and hand over only at the queue.

    The timeline of one call. When an operator in y = model(x) runs (layer five of 2.3):

    • The CPU: prepares the arguments, calls CUDA's interface, puts "run this kernel" on the queue. A few microseconds. Returns.
    • The GPU: at some point this task's turn comes and it executes it. It may take a few microseconds or tens of milliseconds.

    When the CPU returns, the GPU has most likely not started on this task; several others may still be ahead of it.

    Benefit one: the CPU does not wait. It can go straight on to issue the next task. As long as the CPU issues faster than the GPU executes, there are always tasks waiting in the queue and the GPU is never idle. Conversely, if the CPU issues slowly, the queue is often empty and the GPU is waiting for orders (2.3).

    Benefit two: overlap. While the GPU works through the queue, the CPU can do something entirely unrelated: prepare the next batch, write logs, run Python's garbage collection. That time is "hidden" behind the GPU's computation.

    Trouble one: timing out of step. As 3.1 explained: timing an operator with the CPU's clock measures only the few microseconds of "putting it on the queue". To measure the real time, make the CPU wait for the queue to empty (synchronise) before reading the clock. The profiler can report CPU time and GPU time separately precisely because it knows this.

    Trouble two: errors out of step. When a kernel fails on the GPU (an index out of range, say), the CPU has long since run many lines further. The error is only discovered the next time the CPU deals with the GPU, so the line Python's error points to is often not the line that actually went wrong. When hunting such errors, set the environment variable CUDA_LAUNCH_BLOCKING=1, which makes every call wait for its kernel to finish before returning. The program becomes much slower, but the reported location is accurate. It also shows how much asynchrony matters: with this switch on, training slows down noticeably, and the slowdown is what asynchrony normally saves.

    An analogyLike the order rail in a restaurant kitchen: the waiter clips the ticket up and turns to the next table, and the cooks take tickets in order. How fast the waiter writes tickets and how fast the cooks cook are two different things.

    So a line of PyTorch code having "finished" only means its task is in the queue. This brings two benefits and one trouble: the CPU can use the time to prepare later tasks; CPU and GPU work can overlap; the trouble is that timing and error locations both come "out of step".

  2. There need not be only one queue.

  3. 2Streams: in order within one queue, at the same time across different queues

    A stream is the queue of the previous card. Tasks in the same stream execute strictly one after another in the order they were put in; tasks in different streams have no ordering constraint between them, and the GPU can run them at the same time. PyTorch puts all tasks into one stream by default.

    The same stream: in order. Tasks run in the order they were put in; the next starts only when the previous one is done. This guarantee matters: as 2.4 said, after x = x.to(device, non_blocking=True) starts an asynchronous copy, calling model(x) straight away is safe, because the model's first kernel is on the same stream as the copy, queued behind it, and never reads half-copied data.

    Different streams: concurrency. The GPU has separate hardware for different kinds of work: the compute units that run kernels, and copy engines that move data between host and device. Put a copy in stream A and a kernel in stream B, and the two can truly run at the same time. The classic example in the Best Practices Guide does exactly this: split the data into several pieces, put each piece's "copy" and "compute" into their own streams, and the computation of piece k overlaps with the copy of piece k+1.

    Two kernels in two streams can also run at the same time, but they share the same SMs. If one kernel already fills the GPU, the other cannot raise total throughput; the two are merely interleaved. Only when a single kernel cannot fill the GPU (very small kernels) can several streams raise utilisation.

    How streams coordinate. Sometimes a task in stream B must wait for a task in stream A to finish. The way is to put a marker (an event) on A and have B wait for it. The CPU can also wait for a marker, or for a whole stream to empty.

    Where you have already used it.

    • NCCL. As the source walkthrough of 7.1 mentioned, DDP puts all-reduce on a stream of its own. So the gradient synchronisation kernels can run on the GPU at the same time as the backward computation kernels, which is what makes "overlapping communication with computation" possible. "Channels occupying SMs" in 6.2 is these two streams sharing compute units.
    • FSDP's prefetching. The all-gather issued ahead of time is also on its own stream, running alongside the current layer's computation.
    • The profiler's timeline. The GPU part is divided into rows by stream. Computation kernels in one row, NCCL kernels in another, overlapping in time: that is the situation above.

    Using it yourself in PyTorch. torch.cuda.Stream() creates a stream, and with torch.cuda.stream(s): puts the tasks in a block of code into it. Day to day it is rarely needed: single-GPU training is one sequential pipeline, and one stream suits it perfectly. Those who need it are mostly the authors of frameworks and libraries. Be careful with memory: the allocator manages free blocks per stream, and when a tensor is used across streams, you must ensure the ordering yourself.

    An analogyLike checkout lanes in a supermarket: people in the same lane pay in order; open a second lane and the two can check out at the same time. But the total number of cashiers (the GPU's hardware resources) has not changed; the two lanes are sharing them.

    So by default the tasks on the GPU run one after another, and you need not worry about order. To make two things truly overlap (copying and computing, communicating and computing), put them in different streams; NCCL and some internals of PyTorch do exactly this.

  4. The benefit of asynchrony comes from "the CPU does not wait". But some code forces it to.

  5. 3Synchronisation points: whenever the CPU needs an actual value from the GPU, it must stop and wait

    Most of the time the CPU only puts tasks on the queue. But some operations need a computed result from the GPU brought back to the CPU before they can continue: turning a tensor into a Python number, printing its contents, copying it back to main memory, deciding something based on its value. Then the CPU must wait for every task ahead in the queue to finish. Such places are called synchronisation points.

    Which operations synchronise. There is only one criterion: does the CPU need to know the contents of some tensor on the GPU (not just its shape)?

    • loss.item(), float(loss), loss.tolist(): take the values as Python objects.
    • print(tensor): needs the contents to print.
    • tensor.cpu(), tensor.numpy(), .to("cpu") without non_blocking: copy the data back to main memory.
    • if tensor > 0:, while tensor.any():: Python needs the truth value to decide which branch to take.
    • Operators whose result size depends on the data: torch.nonzero, indexing with a boolean mask, torch.unique. The CPU must know how many elements the result has before it can allocate the output.
    • torch.cuda.synchronize(): an explicit request to synchronise.

    By contrast, operations that only use the shape (x.shape, x.size(0), len(x)) do not synchronise: shapes are metadata and always live on the CPU side (2.1).

    Why it is slow. Synchronisation is not extra computation in itself: those tasks have to be done sooner or later. The loss is twofold:

    • While waiting, the CPU cannot issue later tasks. When the synchronisation ends the queue is empty, and the GPU waits for the CPU to fill it again. For models where giving orders is already tight (2.3), this gap turns straight into GPU idle time.
    • The CPU could have used the time for other work (preparing data, handling the previous step's logs), and now just waits.

    The most common one in a training loop.

    for x, y in loader:
    loss = model(x, y)
    loss.backward(); opt.step(); opt.zero_grad()
    running += loss.item()          # synchronises at every step

    The fix: do not take the value; accumulate on the GPU and take it every so many steps.

        running += loss.detach()        # still on the GPU, no synchronisation
    if step % 100 == 0:
        print(running.item() / 100) # synchronise once every 100 steps
        running.zero_()

    (The detach is required; otherwise, as 2.2 explained, every step's computation graph is kept alive.)

    Other common sources. A print left behind from debugging; copying metrics back to the CPU at every step to compute accuracy; torch.cuda.synchronize() sprinkled everywhere "to be safe"; using a tensor's value in Python control flow (which is also the source of graph breaks in 2.5; both have the same root).

    How to find them. In the profiler's results, look for aten::item, aten::_local_scalar_dense, and device-to-host Memcpy. Their CPU time is especially long, not because they are slow themselves but because the CPU waits there for all the GPU tasks before them. So beware of misreading it too: a synchronisation point gets all the asynchronous tasks before it "charged" to itself.

    Synchronisation points are more expensive with several GPUs. As the troubleshooting of 7.1 mentioned: when one process falls a beat behind because of a synchronisation point, the other processes wait for it at the next collective.

    An analogyLike a waiter who has been placing orders non-stop when one table asks "how far along is our food". He can only stand at the pass until the cooks have finished all the earlier tickets before he can answer, and meanwhile he takes no new orders.

    So synchronisation points break the overlap of CPU and GPU. With one in every step of the training loop, part of the benefit of asynchrony is lost. They often hide in code for logging and debugging.

  6. Synchronisation points make the CPU wait. Even without them, giving orders has its own cost. 2.3 described this cost; here is the way to press it to a minimum.

  7. 4CUDA Graphs: record the launches of a string of kernels, and replay them in one go afterwards

    Each kernel launch needs some fixed work from the CPU and the driver. A training step has thousands of kernels, and the sequence of launches is exactly the same at every step. A CUDA Graph "records" this whole string of launches as one object; after that, each step only tells the driver "replay" once, and the cost of thousands of launches becomes the cost of one.

    Back to the sum in 2.3. An operator's cost on the CPU has two layers:

    • The framework layer: Python, the dispatcher, preparing the output.
    • The driver layer: the work needed to hand one kernel launch to the GPU.

    torch.compile (2.5) mainly cuts the first layer. A CUDA Graph cuts the second, and since replaying runs none of the framework's code at all, the first layer is saved as well.

    How it works.

    • Recording. Put a stream into "capture" mode, then run the code to be recorded once as usual. During this pass the kernels are not really executed; the driver just notes "which kernels were launched, with what arguments, and how they depend on each other", forming a graph.
    • Replaying. Each later call to "replay this graph" has the driver submit all the kernels in the graph to the GPU at once, following the recorded dependencies.

    Because the graph records dependencies, the driver can also see which kernels are independent and can run in parallel, something launching them one by one cannot do.

    The limits, all from "what is recorded is fixed".

    • Arguments are fixed. The graph records each kernel's arguments as they were, including the memory addresses of its input and output tensors. So when replaying, the data must sit at the same addresses as during recording. The way: allocate the input tensors before recording; at each step copy the new data into those tensors (rather than using a new tensor), replay, then read the results from the fixed output tensors.
    • Shapes are fixed. With a different shape the kernels' arguments differ, and another graph has to be recorded.
    • No synchronisation points and no data-dependent control flow. During recording no kernel really runs, so no result is available; and whichever branch Python's if took is recorded for good.
    • It takes memory. To keep addresses fixed, the intermediate tensors the graph uses are managed by a dedicated memory pool, not shared with other tensors.

    In PyTorch.

    • Directly: record with torch.cuda.CUDAGraph() and with torch.cuda.graph(g):, replay with g.replay(). The official blog has a complete example of a training loop.
    • Indirectly: torch.compile(model, mode="reduce-overhead") (2.5). The compiler handles fixing the addresses and re-recording for you, and falls back to the ordinary way automatically when the conditions are not met. For most people this is the easier way.

    When it is worth it. Back to the test of 2.3: double the batch; if the time barely changes, it is overhead-bound, and that is when CUDA Graphs work best. Typical beneficiaries are small-batch inference, small networks in reinforcement learning, and the parts of a model whose kernels are especially fragmented. In training large models with large batches, the kernels' own run time far exceeds the launch cost, and the gain is small.

    An analogyLike a set menu at a restaurant: a regular orders the same eight dishes every time. Rather than reading out eight dish names and writing eight tickets each time, make it a set menu: "the usual", and the kitchen works from a fixed ticket.

    So it fights the overhead of giving orders, and works clearly for models with many small kernels. The condition is that every step does exactly the same thing: the same kernels, the same shapes, the data at the same addresses.

  8. Everything so far has been inside one process. Finally, the situation of several processes using one GPU at once, which is common on shared clusters.

  9. 5Several processes sharing one GPU: they take turns by default, not run at the same time

    Each process using a GPU has its own context. By default a GPU executes the tasks of only one context at any moment, and processes take turns in time slices. So two processes get 50% of the time each, not half of the compute units each; and the switching itself has a cost. For several processes to really use one GPU at the same time, a mechanism such as MPS is needed.

    Contexts. The first time a process uses a GPU, the driver creates a context for it: all its state on that GPU, including memory mappings, loaded kernel code, and its streams. The few hundred MB of memory each process permanently takes, mentioned in 2.1, is mostly this.

    The default: time slices. A GPU runs the tasks of only one context at a time. With two processes, the GPU runs process A for a short while, switches to process B for a short while, then switches back.

    • Each process gets about half the time.
    • During A's turn, even if A's kernels use only a small part of the SMs, the rest stay idle and B cannot use them.
    • Each switch has a cost.
    • The utilisation nvidia-smi shows is for the whole GPU and may look high, while each process's actual throughput is less than half of what it gets alone.

    Memory, on the other hand, is truly divided: the two processes' memory together cannot exceed the GPU's capacity.

    MPS (the Multi-Process Service). A server process provided by NVIDIA. With it on, all processes' tasks are handed to it, and it merges them into one context to submit to the GPU. So kernels from different processes can really run at the same time, sharing the SMs. For many small jobs that each cannot fill the GPU (small-model inference, small experiments in a hyperparameter search), total throughput can rise clearly. The price is weaker isolation between processes: a serious error in one process may affect the others.

    Two "harder" ways of dividing.

    • MIG: cuts one GPU at the hardware level into several isolated small instances, each with a fixed share of compute units and memory. Good isolation, but fixed shares, not flexible.
    • Time-slice sharing at the level of the cluster scheduler: the scheduler assigns the same GPU to several containers, and underneath it is still taking turns. 8.2, on GPUs in Kubernetes, comes back to these.

    The link to training.

    • In multi-GPU training each process has a GPU to itself, so this problem does not arise. But if a configuration error puts two training processes on the same GPU (the mapping between processes and GPUs set wrongly, say), the signs are double memory use on that GPU, both processes at half speed, and, through synchronisation, every other process slowed down too (7.1).
    • When troubleshooting "it suddenly got slower", first take a look with nvidia-smi at which processes are on each GPU. A process that is not yours is the answer.
    • Running training and evaluation on the same GPU at once, or leaving a notebook open that holds the GPU, is the same situation.

    An analogyLike a meeting room shared by two teams: by default they take turns, one team inside while the other waits outside. Even if only three people are in there and half the seats are empty, the other team cannot come in.

    So two small jobs that can each fill only half a GPU do not fill it when put on the same GPU. On a shared cluster, "my job got slower" is sometimes just a new neighbour on the same GPU.

Putting it together

A CPU call to CUDA only puts a task on a queue. One queue is called a stream, executed in order inside; different streams can run concurrently, and overlapping copies with computation, or communication with computation, relies on this. Operations that bring a result back to the CPU are synchronisation points, making the CPU wait for the queue to empty. A CUDA Graph records a string of kernel launches and replays them as a whole, saving the overhead of giving each order. Several processes sharing one GPU take turns by default.
