Explanation

  1. 1Triton lets you think in "blocks"

    One program instance in Triton handles a whole block of data, with vectorised operations; how the block is divided among threads, how memory accesses coalesce, whether to use shared memory and when to synchronise are all decided by the compiler.

    CUDA's view: one thread. As 3.2 explained, when writing a CUDA kernel you stand in the place of one thread: which thread am I, which element am I responsible for. For good performance you also have to handle the things of part 3 yourself: make neighbouring threads' memory accesses coalesce, decide which data goes into shared memory, synchronise in the right places, and handle the partial block at the boundary.

    Triton's view: a block of data. Triton is a language for writing kernels, embedded in Python. One program instance is responsible for a whole block of data (say a 64×64 tile), and the code operates on "a block", written much like NumPy:

    @triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(0)                     # which program instance am I
    offs = pid * BLOCK + tl.arange(0, BLOCK)   # the indices of the block I am responsible for
    mask = offs < n                            # the last block may be partial
    x = tl.load(x_ptr + offs, mask=mask)       # read a whole block
    y = tl.load(y_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, x + y, mask=mask) # write a whole block

    (This is the structure of vector addition from the official introductory tutorial, with details left out.)

    No "thread" appears in the code. x + y adds a whole block; how the elements of the block are divided among threads, and which ones each thread reads, is decided by the compiler.

    What the compiler does for you.

    • Distributes the operations within the block among the threads of a block.
    • Arranges memory accesses so they coalesce (3.4).
    • Uses shared memory where needed, inserting the necessary synchronisation.
    • For operations like matrix multiplication, generates instructions that use Tensor Cores.
    • Handles boundaries uniformly with mask, so you need not write a separate branch.

    What you still decide. How the data is cut into blocks, how large the blocks are, and how the loop over blocks is written. That is, the structure at the level of the algorithm. The tiled matrix multiplication of 3.3 written in Triton is still "the outer loop walks the blocks along K, each time reading in two tiles, multiplying and accumulating", only every step operates on blocks rather than single elements.

    So Triton does not bypass the knowledge of part 3; it automates its mechanical half. What you need to understand is "why tile, and which level of storage the tiles go in"; you no longer need to write "which thread reads which address" by hand.

    The link to torch.compile. As 2.5 explained, what Inductor generates on the GPU is Triton functions just like this. The code printed with TORCH_LOGS=output_code has the same structure as the example above: work out the indices of this block, read the same block of several inputs, do a chain of operations, write it out.

    An analogyCUDA is like giving orders to each soldier; Triton is like giving orders to each company, with the company commander (the compiler) arranging how the work is divided inside.

    So Triton code is much shorter than CUDA, and most of the optimisations learned in part 3, coalescing and tiling, are done automatically; your job is to think through how to cut the data into blocks and how large they should be.

  2. The example above has a parameter BLOCK. Its value matters a lot for performance, yet is hard to settle by reasoning.

  3. 2How large should the block be? Let it try for itself

    The best block size, number of warps and number of pipeline stages depend on the shapes of the matrices and on the specific GPU. Triton's autotune runs several candidate configurations and remembers the fastest.

    What the parameters are. A Triton kernel usually has several parameters that affect performance but not the result:

    • The block size in each direction (matrix multiplication has three: M, N and K).
    • How many warps each program instance uses.
    • The number of stages in the software pipeline (how many steps ahead to prefetch data; the double buffering of 4.5 is two stages).

    Why it is hard to work out. The block size involves several conflicting factors:

    • Large blocks: data read in from memory is reused more times, and arithmetic intensity is higher (3.3).
    • Blocks too large: shared memory and registers cannot hold them; fewer blocks can be resident on an SM at once, and memory latency cannot be hidden (occupancy, 3.3).
    • The best compromise depends on the specific GPU model (how large its shared memory is, how many registers it has), the shapes of the matrices, and the data type.

    The relationships among these factors have no simple formula. The same code, on an A100 or an H100, for 1024×1024 or 128×8192 matrices, may have a different best configuration in each case.

    The way: try them all. Add a decorator to the kernel listing a few candidate configurations:

    @triton.autotune(
    configs=[
        triton.Config({"BLOCK_M": 128, "BLOCK_N": 64,  "BLOCK_K": 32}, num_warps=4, num_stages=3),
        triton.Config({"BLOCK_M": 64,  "BLOCK_N": 64,  "BLOCK_K": 32}, num_warps=4, num_stages=4),
        ...
    ],
    key=["M", "N", "K"],          # search again when any of these values changes
)

    The first time the kernel is called with a given shape, Triton compiles and runs every configuration and notes the fastest. Later calls with the same shape use it directly.

    Costs and cautions.

    • The first call is slow (it compiles and runs every candidate). Always skip it when measuring performance.
    • Every new combination of the values in key triggers a new search. Where shapes vary a lot, either limit the number of candidates or put the shapes into a few size classes.
    • It only chooses among the candidates you give. If they are all poor, so is the choice.

    This is a very common attitude in performance engineering: when the model is too complex to reason through, do not derive; measure. "Measure first, then change" from 0.2 is automated here. The max-autotune mode of torch.compile (2.5) uses the same idea.

    An analogyLike getting glasses: rather than guessing the prescription from experience, try several lenses in turn.

    So the same kernel adapts to different shapes and GPUs; the first run being a bit slow is it searching for a configuration.

  4. If Triton is convenient and performs well, is there any need to learn CUDA?

  5. 3Use Triton first; write CUDA only when it is shown not to be enough

    Triton covers most fused operators and many matrix multiplication cases, often performing close to hand-written CUDA; but when you need fine control over warp-level operations, special data layouts or the newest hardware features, you still have to go back to CUDA or CUTLASS.

    What Triton is good at.

    • Fused element-wise operations and reductions (4.2): its main use, and what torch.compile uses it for.
    • Regular, dense operations that can be processed by blocks: matrix multiplication and its variants, attention, normalisation.
    • New operators that need quick experiments: short code, quick to change, in the same Python file as PyTorch.

    In these cases a kernel written in Triton usually reaches eighty or ninety percent of hand-written CUDA or matches it, with a fraction of the code.

    What it is not good at.

    • Algorithms that need fine control over the behaviour of each warp and each thread. Some of the parallel patterns of 3.5 (such as scans that need threads to cooperate in particular ways) are hard to express with the "block" abstraction.
    • Irregular data: sparse matrices, graphs, sequences of uneven length.
    • Special memory layouts, or a proprietary feature of the newest hardware that the compiler does not yet support.
    • Chasing the last ten-odd percent of performance: library authors (cuBLAS, cuDNN) still use lower-level means.

    A practical order of decisions (an order often recommended; here are the reasons):

    • Libraries first. Matrix multiplication, convolution, standard attention: you are very unlikely to beat the library implementations.
    • Then the compiler. For a chain of operations you assembled yourself, first see whether torch.compile fuses it well. Zero cost in code.
    • Only then Triton. For patterns the compiler cannot fuse, or fuses badly, write one by hand in Triton.
    • CUDA last. Only when the profiler shows this kernel is the bottleneck, the roofline shows it is far from the hardware's limit, and Triton cannot express the optimisation you want.

    Each level down costs an order of magnitude more to develop and maintain, so go down only with evidence.

    Then why did part 3 spend so long on CUDA? Because your goal is to read and troubleshoot, not only to write. The code Triton generates, the kernels in libraries, the metrics the profiler reports, all speak the language of warps, shared memory and coalesced access. Without understanding the layer underneath, you cannot understand why the layer above is fast or slow.

    An analogyLike fitting out a home: for most of it, off-the-shelf furniture is enough; only the odd-sized corners are worth having a carpenter make something to measure.

    So use Triton first to get a version that is fast enough quickly; only when the profiler shows it is the bottleneck, and still far from the hardware's limit, is it worth writing CUDA by hand.

Putting it together

Triton lets you write kernels in units of blocks; how threads are assigned within a block, how memory accesses coalesce and how shared memory is used are the compiler's job. Parameters such as the block size are searched with autotune. In practice, use Triton first, and write CUDA by hand only when the profiler shows it is not enough and it is still far from the hardware's limit.
