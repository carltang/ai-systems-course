第 10 部分 · 强化学习（选读）10.3 强化学习的系统形态

这一单元回答强化学习的训练系统，和前面讲的大模型训练有什么不一样？
承接 10.2，并回到 0.1 的管道图：强化学习的“数据供给”不是读硬盘，而是和环境交互出来的。

线索是：强化学习的训练数据要靠运行环境来产生，这改变了管道的形状 → 经典的应对是把采集和学习分给不同的进程 → 更彻底的办法是把环境本身搬到 GPU 上 → 另一个方向是把产生的数据存起来多用几次 → 最后用第 0 部分的语言把它和大模型训练对照一遍。你会发现需要的知识前面都学过，只是瓶颈换了位置。

  1. 数据不是读出来的，是和环境交互“跑”出来的
  2. 采集和学习分开：很多个 actor，少数几个 learner
  3. 把环境搬上 GPU：成千上万个仿真同时跑
  4. 经验回放：把数据存起来，反复用
  5. 对照第 0 部分：同一条管道，不同的瓶颈

讲解

  1. 1数据不是读出来的，是和环境交互“跑”出来的

    大模型训练的数据躺在硬盘上，管道的第一步是“读”。强化学习的数据要靠运行来产生：每一步都要让策略网络做一次推理选出动作，再让环境的仿真程序向前推进一步。训练的大部分时间常常花在这上面，而不是花在反向传播上。

    回顾 0.1 的管道。 大模型训练的一步：读数据 → 预处理 → 拷上 GPU → 前向反向 → 同步梯度 → 更新参数。数据是现成的，第一步只是 IO。

    强化学习的一步。 以 PPO 为例（10.2）：

    • 采集。 重复几百到几千次：策略网络看当前的状态，推理出动作；环境执行动作，算出下一个状态和奖励。把这些记下来。
    • 学习。 用刚采集的数据算优势，做几轮前向反向，更新策略和评论家。
    • 扔掉数据，用新策略重新采集。

    采集阶段替代了“读数据”，而它本身包含大量的计算。

    采集阶段有两种计算，性格完全不同。

    • *环境的仿真。* 物理引擎计算碰撞和受力、游戏模拟器执行一帧、或者（在语言模型的场景）运行一段代码来检查答案。传统上这些是 CPU 上的程序，逻辑复杂、分支多，每个环境实例是串行的。
    • *策略的推理。* 一次神经网络的前向。强化学习里的网络通常很小（几层的 MLP 或小的卷积网络），单次推理的计算量很小。

    两者是交替进行的：推理一次，仿真一步，再推理一次。它们之间有严格的先后依赖，和 1.4 讲的自回归生成一样，无法把一条轨迹内部并行化。

    时间花在哪。 很多强化学习的任务里，仿真占了大头。网络小，反向传播很快；而要学会一个任务可能需要几亿甚至几十亿步的交互。于是典型的画面是：几十上百个 CPU 核满负荷地跑仿真，GPU 的利用率只有百分之十几。按 0.2 的说法，这不代表系统有毛病，而是瓶颈根本不在 GPU 上。

    并行的方向。 一条轨迹内部不能并行，但可以同时跑很多条：开 N 个环境的副本，每一步让策略网络对 N 个状态做一次批量的推理，得到 N 个动作，再让 N 个环境各走一步。这叫向量化环境。它把策略推理变成了有 batch 的运算（9.1 讲的批处理的好处在这里同样成立），仿真则分给多个 CPU 核。后面三节都是这个思路的不同实现。

    衡量的指标。 强化学习系统的吞吐通常用“每秒环境步数”来衡量。一个好的实现和一个朴素的实现，可以差出几个数量级。

    打个比方大模型训练像一家有现成原料仓库的工厂，只管加工。强化学习像一家自己有农场的餐厅：先得种菜，而且种什么菜、怎么种，取决于厨师最近的手艺。厨房再快，菜没长出来也只能等。

    所以强化学习系统设计的核心问题是“怎样更快地产生数据”。评价它的吞吐，看的是每秒产生多少步环境交互，而不只是每秒训练多少个样本。

    承接 PPO：每次只把策略改一小步训练的一步是一条串联的管道，最慢的一段决定速度因果掩码：训练时整段并行，生成时一词一词
    后面会用到 采集和学习分开：很多个 actor，少数几个 learner
    出处IMPALA 论文Hugging Face Deep RL Course
  2. 采集是瓶颈，而且天然可以并行。最直接的做法是把它分出去。

  3. 2采集和学习分开：很多个 actor，少数几个 learner

    经典的分布式强化学习架构把系统分成两种角色。actor 进程运行环境和策略，只负责产生数据；它们数量很多，跑在 CPU 上。learner 进程从 actor 那里接收数据，在 GPU 上做反向传播更新模型，再把新的参数发回给 actor。两边各按各的节奏运行，互不等待。

    为什么要分开。 采集要的是大量的 CPU 核，学习要的是 GPU。把它们绑在一个同步的循环里（上一节的“采集一批，学习一轮”），GPU 在采集时闲着，CPU 在学习时闲着。分开之后各自满负荷运行。

    同步的版本先看一眼。 一个 learner，N 个环境。每一步：N 个环境各给出一个状态 → 策略网络批量推理 → N 个环境各走一步。问题是每一步都要等最慢的那个环境。环境的每一步耗时常常很不均匀（游戏里某些画面计算量大，物理仿真里碰撞多的时刻更慢），所有人都被最慢的拖住。7.1 讲的慢节点问题，在这里每一步都在发生。

    异步的版本：IMPALA。

    • 每个 actor 有一份策略参数的本地副本，独立地和自己的环境交互，攒够一段轨迹就发给 learner，然后不等任何人，继续采集。
    • learner 持续地从队列里取出收到的轨迹，组成 batch，做反向传播。
    • actor 定期从 learner 拉取最新的参数。

    没有任何一方在等另一方。actor 可以有几百上千个，分布在很多台机器上。

    新问题：策略滞后。 actor 采集一段轨迹期间，learner 已经更新了好几次。等这段轨迹到达 learner 时，产生它的策略已经是“旧版本”了。10.2 讲过，策略梯度要求数据来自当前的策略。用旧策略的数据直接算，会有偏差。

    IMPALA 的贡献之一是一种修正方法（叫 V-trace）：根据“新策略选这个动作的概率 ÷ 旧策略选它的概率”，给数据重新加权，把旧数据“折算”成对新策略有效的信号。这个比值你在 PPO 里见过，两处的想法是相通的。

    另一种分法：Ape-X。 面向价值路线（DQN 类）。很多 actor 把经验写进一个共享的回放缓冲区，learner 从缓冲区里抽样学习。因为 Q-learning 本来就是异策略的，旧数据可以直接用，不需要修正。

    推理放在哪。 actor 要做策略推理。两种安排：

    • 每个 actor 在自己的 CPU 上推理：简单，但网络稍大就慢。
    • 集中推理：actor 只跑环境，把状态发给一个在 GPU 上的推理服务，由它把来自很多 actor 的请求批在一起推理，再把动作发回去。这其实就是 9.3 讲的推理服务：请求陆续到达，要在批大小和延迟之间权衡。强化学习的训练系统里嵌着一个小型的推理服务系统。

    用第 0 部分的眼光看。 这套架构是“用别的活把等待填满”：采集和学习重叠进行。代价和别处一样：数据在途中，会“变旧”。7.1 的 DDP 让通信和计算重叠时没有这个问题，因为梯度不会过时；这里的数据会过时，所以多了一步修正。

    打个比方像一家报社：很多记者在外面跑新闻（actor），把稿子陆续发回来；编辑部（learner）不停地处理收到的稿件，并时不时把最新的采编要求通知给记者。记者不用等编辑，编辑也不用等某一位记者。

    所以这套架构能把采集的规模扩到几千个 CPU 核。它带来一个新问题：actor 手里的策略总是比 learner 的旧一点，用旧策略产生的数据去更新新策略，需要做修正。

    承接 数据不是读出来的，是和环境交互“跑”出来的PPO：每次只把策略改一小步五个思想会在每一层反复出现扩展效率：多卡吞吐 ÷（单卡吞吐 × 卡数）
    后面会用到 把环境搬上 GPU：成千上万个仿真同时跑游戏、推荐、调度：几个经典的应用领域

  4. 上一节是把采集分给很多 CPU。还有一个更彻底的方向：让采集根本不需要 CPU。

  5. 3把环境搬上 GPU：成千上万个仿真同时跑

    仿真在 CPU、网络在 GPU 时，每一步都要在两者之间来回传数据。更彻底的办法是把仿真本身也写成 GPU 上的张量运算：几千上万个环境的状态存在一个大张量里，一次运算让所有环境同时前进一步。整个采集和学习的循环都在 GPU 上，数据不离开显存。

    传统做法的三处开销。

    • 仿真在 CPU 上，每个环境实例占一个核的一部分。要几千个环境，就要几百个核。
    • 每一步，状态要从主内存拷到显存（给网络推理），动作再从显存拷回主内存（给仿真）。数据量不大，但每一步都要过一次 PCIe，并且是同步的。3.6 讲过，这样的同步点会打断 GPU 的任务队列。
    • 策略网络很小，每次推理只有几个很小的 kernel。GPU 大部分时间在等 CPU 把下一步的状态算出来。2.3 的“等发令”在这里非常典型。

    GPU 上的仿真。 以物理仿真为例。每个环境的状态是一组数（各个物体的位置、速度、关节角度）。把 N 个环境的状态叠成一个张量，第一维是环境的编号。物理引擎的一步（算受力、检测碰撞、积分得到新的位置和速度）写成对这个张量的批量运算。对 GPU 来说，这和神经网络的一次前向没有本质区别。

    NVIDIA 的 Isaac Gym 是这个方向有代表性的工作：物理仿真、观测的计算、奖励的计算、策略的推理和训练，全部在同一张 GPU 上，中间的数据一直是显存里的张量。论文报告在一张卡上同时运行几千到上万个机器人环境，一些原来需要一个 CPU 集群跑几天的任务，缩短到了几十分钟到几小时。

    为什么这么有效，用前面的话来说。

    • 第 3 部分：GPU 擅长的是对大量数据做同样的运算。一万个环境执行同一套物理规则，正是这种情形。
    • 0.1：没有了 CPU 和 GPU 之间的往返，“等数据”和“等发令”同时消失。
    • 9.1：策略推理的 batch 从几十变成了一万，小网络也能把 GPU 用起来。

    适用的前提。

    • 仿真的逻辑要能批量化。物理规则是统一的，适合。逻辑复杂、分支很多、每个实例走的路径都不同的仿真器（很多现成的游戏、需要调用外部程序的环境）很难搬上 GPU。3.4 讲过分支发散对 GPU 的代价。
    • 所有环境的状态要放得下显存。带相机图像的环境，每个实例的观测很大，能并行的数量就少得多。
    • 仿真要足够逼真，学到的策略才能用到真实世界（10.4）。为了速度而简化的物理，可能让策略学到只在仿真里成立的窍门。

    算法也要跟着变。 一万个环境并行时，每个环境只需要走很短的一段（几十步），就凑够了一大批数据。数据的特点从“少数几条很长的轨迹”变成了“海量很短的片段”。PPO 这类算法天然适合这种模式，这也是它在机器人训练里成为主流的一个原因。

    打个比方以前是一万个工人各自在工位上手工做一个零件，每做一步都要把半成品送到质检室再取回来。现在换成一台冲床，一次压出一万个零件，质检就在旁边的同一条线上。

    所以一张 GPU 就能达到以前需要一个 CPU 集群才有的采集速度。机器人领域近几年的快速进展，很大程度上来自这个变化。它的前提是仿真本身能写成规整的、可以批量执行的运算。

    承接 采集和学习分开：很多个 actor，少数几个 learner同步点：只要 CPU 需要 GPU 上的一个具体的值，它就得停下来等这条路每次要花若干微秒；模型小、算子碎时，它就成了瓶颈CPU 是超跑，GPU 是公交批处理：读一次权重，服务一批请求
    后面会用到 经验回放：把数据存起来，反复用机器人与控制：在仿真里训练，迁移到真机

  6. 前两节都在让数据产生得更快。另一个方向是让每条数据多发挥几次作用。

  7. 4经验回放：把数据存起来，反复用

    产生数据很贵，那就别用一次就扔。经验回放把智能体经历过的每一步存进一个大缓冲区，训练时从中反复抽样。每条数据平均能被用上很多次，需要的环境交互次数因此少得多。它只适用于能使用旧数据的算法，也就是 10.2 讲的异策略方法。

    两种效率。

    • *样本效率*：学会一个任务需要多少步环境交互。
    • *计算效率（墙上时间）*：学会一个任务需要多长时间、多少算力。

    它们不是一回事。一个算法可能需要十倍的样本，但如果每个样本的产生和处理都快一百倍，它反而更早学会。

    回放缓冲区。 一个容量很大的存储（比如一百万步），存着最近的经验：（状态，动作，奖励，下一个状态）。新数据进来，最老的被挤出去。训练时每次从中随机抽一个 batch。

    10.2 讲 DQN 时说过它的两个作用：打破相邻样本之间的相关性；让每条数据被多次使用。这里关心的是后者。带回放的方法，每采集一步数据可以做好几次梯度更新；PPO 每条数据只用几轮就扔。

    为什么只能是异策略。 缓冲区里的数据是过去很多个不同版本的策略产生的。10.2 讲过：

    • Q-learning 类的方法只需要“环境里真实发生过的一步转移”，不在乎是哪个策略产生的。可以直接用。
    • 策略梯度类的方法要求数据来自当前策略。旧数据不能直接用（上上节的 V-trace 那样的修正只能处理“稍微旧一点”的数据）。

    所以有回放的系统，核心算法通常是价值路线，或者是为了能用旧数据而专门设计的 actor-critic 变体。

    不是所有的经验都一样有用。 均匀地随机抽样，大部分抽到的是早就学会了的平凡经验。优先回放的做法是：TD 误差大的经验（“这一步的结果出乎我的意料”）被抽中的概率更高。上上节的 Ape-X 就是分布式的优先回放。

    怎么选。

    用完即扔（PPO 类）带回放（DQN 类、异策略 actor-critic）
    每条数据用几次几次很多次
    样本效率低高
    稳定性、调参容易较难（10.2 的致命三角）
    适合仿真极便宜，可以大规模并行每步交互都很贵
    瓶颈常在仿真的速度学习的速度（GPU）

    有了上一节的 GPU 并行仿真之后，天平向左边倾斜了很多：数据便宜到几乎不用在乎样本效率，简单稳定的 PPO 就成了首选。而在真实的机器人上直接学习、或者奖励需要人来给的场景，样本效率仍然是第一位的。

    回放缓冲区自己也是个系统问题。 存一百万步带图像的经验要几十 GB；从中随机抽样是随机访存（0.3）；分布式的时候它是一个被很多 actor 写、被 learner 读的共享服务。2.4 讲的数据加载的那些考虑，在这里换了一种形式又出现了。

    打个比方像做题：一本习题集只做一遍就扔，要学会得买很多本。把做过的题整理成错题本，隔一阵拿出来重做，同样的题目能学到更多。

    所以算法的选择和系统的形态是连在一起的：仿真便宜时，用 PPO 这类“用完即扔”的方法，靠并行堆数量；每条数据都很贵时（真机、需要人参与），用带回放的方法，靠反复使用提高效率。

    承接 把环境搬上 GPU：成千上万个仿真同时跑价值路线：学会给每个动作打分，再挑分数最高的存储层次：数据每远一层，就慢一到三个数量级

  9. 5对照第 0 部分：同一条管道，不同的瓶颈

    把强化学习的训练放回 0.1 的框架里看，需要的知识前面都学过，只是各段的轻重变了。大模型训练的模型大、数据现成，瓶颈在计算和通信；强化学习的模型通常小、数据要现产，瓶颈在数据的产生和 CPU 与 GPU 之间的协调。

    逐项对照。

    大模型训练强化学习训练（典型情况）
    模型大小几亿到几千亿参数常常只有几十万到几千万
    数据从哪来存储环境仿真 + 策略推理
    等数据一般不是主要问题常常是最大的瓶颈
    等发令大模型里可以忽略小网络、小 kernel，很突出
    等计算主要矛盾（矩阵乘法）通常不是；网络大了才是
    等别的卡多机时的主要矛盾很多任务一张卡就够
    GPU 利用率应该接近满低是常态
    衡量吞吐token/秒、MFU环境步数/秒

    前面哪些单元直接用得上。

    • 0.2：GPU 利用率低，先分清是系统有问题，还是瓶颈本来就不在 GPU。在强化学习里常常是后者。
    • 2.3、3.6：小网络的推理是开销受限的。torch.compile、CUDA Graph、把 batch 开大，在这里效果明显。CPU 仿真和 GPU 推理之间的每一次往返都是同步点。
    • 2.4：环境的并行和 DataLoader 的 worker 是同一类问题：多进程、进程间传数据、CPU 核不够。
    • 5.1：CPU 仿真很重时，CPU 的核数、NUMA 的位置比 GPU 的型号更重要。
    • 9.1、9.3：集中式的策略推理就是一个小型的推理服务。
    • 7.4：训练时间长、进程多，同样需要检查点和容错。actor 的故障比较好处理（少一个只是数据来得慢一点），learner 要有检查点。

    例外：模型很大的强化学习。 上面说的是“小网络 + 仿真环境”的经典情形。当策略本身是一个大语言模型时（10.4），情况倒过来了：

    • 采集阶段 = 让大模型生成文本，这是 9.1 的 decode，很贵；
    • 学习阶段 = 大模型的反向传播，是第 7 部分的分布式训练；
    • 环境（比如执行代码、检查答案）相对便宜，但可能很慢、耗时不均匀。

    这时的系统是“一个推理集群 + 一个训练集群”的组合，这门课前面九个部分的内容几乎全部用得上。

    一个统一的看法。 不管是哪种训练，问的都是同样的几个问题：数据从哪来、多快；计算在哪做、被什么限制；各部分之间怎样协调、谁在等谁。强化学习没有带来新的原理，它只是把 0.1 那条管道的各段重新排了一遍轻重。这也是这门课从“管道和四种等”讲起的原因：换一个领域，这套问法照样管用。

    打个比方同样是开餐厅，一家是大型中央厨房，食材成车运来，难处在灶台够不够、几个厨房怎么协作；另一家是自己种菜的小馆子，灶台常常闲着，难处在菜长得太慢。经营的道理相通，头疼的地方不同。

    所以排查强化学习训练的性能，用的还是 11.1 的那套办法：先量，再拆，找最大的一段。只是答案多半会落在“等数据”和“等发令”上，而不是矩阵乘法上。

    承接 经验回放：把数据存起来，反复用管道上的“慢”只有四种：等数据、等计算、等发令、等别的卡GPU 利用率量的是“有没有在忙”，不是“忙得值不值”这条路每次要花若干微秒；模型小、算子碎时，它就成了瓶颈每个参数调的是管道的哪一站
    后面会用到 训练推理能力：用可以验证的结果当奖励什么问题适合用强化学习

串起来

强化学习的数据是跑出来的：环境的仿真和策略的推理占了大部分时间。经典的架构把采集（actor）和学习（learner）分开，用很多 CPU 进程喂少数 GPU。GPU 上的并行仿真把环境也变成了张量运算，省掉了 CPU 和 GPU 之间的来回。经验回放让数据被反复使用。和大模型训练相比，它更常卡在等数据和等发令上。

考考自己

不看讲解，用自己的话讲一遍。

  1. 强化学习训练的管道和大模型训练的管道有什么不同？它的时间主要花在哪里？
  2. actor-learner 架构里两种进程各做什么？actor 和 learner 不同步带来了什么问题，怎样处理？
  3. GPU 并行仿真相对于“CPU 仿真 + GPU 网络”省掉了什么？它适用的前提是什么？
  4. 经验回放解决什么问题？为什么它只能用于异策略的算法？怎样在“样本效率”和“计算效率”之间选择？
  5. 用第 0 部分的四种“等”来分析，强化学习训练的瓶颈通常在哪里？和大模型训练有什么不同？
