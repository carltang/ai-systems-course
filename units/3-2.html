第 3 部分 · GPU 与 CUDA 执行模型3.2 第一个 CUDA kernel

这一单元回答怎样让成千上万个线程各自找到自己的那份工作？
承接 3.1：GPU 的长处是同时做大量相同的活，这一单元学怎么把活分给线程。

上一单元说 GPU 擅长“同时做大量相同的活”。这一单元回答：这些活具体怎么分下去？线索是：只写一个线程的代码 → 每个线程靠编号找到自己的数据 → 数据先得从 CPU 搬到 GPU → 线程按 block 分组，组与组之间互不依赖。

  1. 只写一个线程的代码，让它跑一百万份
  2. 线程的门牌号：blockIdx × blockDim + threadIdx
  3. CPU 和 GPU 各有一块内存，中间是一条窄路
  4. 块与块互不等待，所以同一个程序能在大卡小卡上都跑

讲解

  1. 1只写一个线程的代码，让它跑一百万份

    CUDA kernel 描述的是“一个线程做什么”。启动 kernel 时指定开多少线程，所有线程执行同一份代码，只是各自处理不同的数据，这叫 SPMD（single program, multiple data）。并行不是写出来的，是“开”出来的。

    在 CPU 上给数组每个元素加 1，你会写一个循环：

    for (int i = 0; i < n; i++) c[i] = a[i] + b[i];

    在 CUDA 里，循环消失了。你只写循环体，也就是“第 i 个元素怎么算”：

    __global__ void add(float* a, float* b, float* c, int n) {
    int i = /* 我是第几号线程 */;
    if (i < n) c[i] = a[i] + b[i];
}

    然后在启动时说“开 n 个线程来执行它”。n 个线程同时运行这同一段代码，各自的 i 不同。

    这就是 SPMD（single program, multiple data）：程序只有一份，数据有很多份。它和上一单元的结论直接对应：GPU 擅长大量相同的工作，kernel 就是对“相同的工作”的描述。

    因此把 CPU 代码搬到 GPU 上，第一步总是找出那个“每次迭代互不依赖”的循环：循环变量变成线程编号，循环体变成 kernel。如果各次迭代互相依赖（比如第 i 步要用第 i−1 步的结果），就不能直接这样做，那是 3.5 的话题。

    打个比方像发给一百万个工人同一张工作说明：每个人照着同一张说明干活，只是凭自己的工号去领不同的料。

    所以写 kernel 的思路是：先想清楚“一个元素怎么算”，再想“第几号线程负责哪个元素”。CPU 代码里的循环，往往变成了线程。

    后面会用到 线程的门牌号：blockIdx × blockDim + threadIdx归约就是淘汰赛：n 个数，log n 轮决出结果
    出处PMPP §2.5
  2. 每个线程执行同一段代码，那它怎么知道自己该处理哪个元素？靠的是它的编号。

  3. 2线程的门牌号：blockIdx × blockDim + threadIdx

    线程分两层组织：网格（grid）由线程块（block）组成，块里是线程。一个线程的全局编号 = 块号 × 每块线程数 + 块内编号，用它找到自己负责的数据。为了凑整，开出的线程通常比数据多，多出来的必须用 if (i < n) 挡住。

    线程不是一个平铺的大列表，而是分两层：若干线程组成一个 block，若干 block 组成 grid。每个线程能读到三个内置变量：blockIdx（我在第几个 block）、blockDim（每个 block 有多少线程）、threadIdx（我在 block 里排第几）。

    全局编号就是：i = blockIdx.x * blockDim.x + threadIdx.x。比如每个 block 256 个线程，第 3 个 block 里的第 10 号线程，全局编号是 3 × 256 + 10 = 778，它就负责 c[778]。

    为什么要越界检查？因为线程只能按整个 block 来开。有 1000 个元素、每个 block 256 个线程时，要开 ⌈1000/256⌉ = 4 个 block，一共 1024 个线程。编号 1000 到 1023 的这 24 个线程没有对应的数据，如果不拦住，它们会去读写数组后面不属于你的内存。

    二维的情况（图片、矩阵）完全一样，只是 x、y 两个方向各算一次：列号用 x 方向的三个变量，行号用 y 方向的三个变量。

    例子：处理一张 1920×1080 的图片，grid 要开多大？

    假设每个 block 取 16×16 = 256 个线程，一个线程处理一个像素。

    • x 方向（宽 1920）：1920 ÷ 16 = 120，正好 120 个 block。
    • y 方向（高 1080）：1080 ÷ 16 = 67.5，要向上取整，68 个 block。

    所以 grid 是 120×68，一共 8160 个 block、约 209 万个线程。线程覆盖的范围是 1920×1088，比图片多出 8 行（15360 个线程），这些线程必须被越界检查拦住。

    kernel 里每个线程这样找到自己的像素：

    int col = blockIdx.x * blockDim.x + threadIdx.x;
int row = blockIdx.y * blockDim.y + threadIdx.y;
if (col < width && row < height) {
    int i = row * width + col;       // 图片按行存：第 row 行第 col 列
    out[i] = /* 用 in[i] 算出结果 */;
}

    向上取整有一个常用写法：(n + blockSize - 1) / blockSize，用整数除法就能得到 ⌈n / blockSize⌉。

    打个比方像用“楼号 × 每栋户数 + 房号”算出全小区的门牌号；最后一栋没住满，空房间不能去敲门。

    所以每个 kernel 的第一行几乎都是算下标，第二行是越界检查；图片、矩阵这样的二维数据，就用 x、y 两个方向分别算出列和行。

  4. 线程找到了自己的位置，但它要处理的数据在哪里？一开始它在 CPU 这边的内存里，而 GPU 访问不到那里。

  5. 3CPU 和 GPU 各有一块内存，中间是一条窄路

    主机内存和显存是分开的，数据要通过 PCIe 拷过去。显存带宽在每秒上千 GB 的量级，PCIe 只有每秒几十 GB，差了几十倍。

    CPU 用的内存（主机内存）和 GPU 用的内存（显存）是两块独立的存储，中间靠 PCIe 总线连接。GPU 上的 kernel 只能读写显存，所以数据必须先拷过去，结果需要时再拷回来。

    问题在于这条通道很窄。GPU 读写自己的显存，速度在每秒几百到上千 GB；而 PCIe 的传输速度大约是每秒十几到几十 GB。拷贝 1 GB 的数据要几十毫秒，而 GPU 对 1 GB 数据做一次逐元素运算只要几毫秒。也就是说，搬一次数据的时间够算十次。

    由此得到一条实用的规则：数据进了 GPU 就别轻易出来。把一长串运算都在 GPU 上连着做完，最后只把需要的结果拷回去。

    训练循环里最常见的坑是每一步都调用 loss.item() 或 .cpu()。它们不仅触发一次拷贝，还会让 CPU 停下来等 GPU 做完前面所有任务（因为 GPU 是异步的，见 3.1）。偶尔打印一次没问题，每一步都调用就会明显变慢。

    打个比方工厂（GPU）里面搬运很快，但原料仓库（CPU 内存）在城外，中间只有一条小路。

    所以数据要尽量一直留在 GPU 上，在上面连续做完多步计算；频繁在 CPU 和 GPU 之间来回拷贝，往往比计算本身还慢。PyTorch 里的 .cpu()、.item() 都会触发拷贝和同步。

    承接 Python 只是在点单：GPU 是异步执行的内存里的数据会被操作系统挪动，交给设备之前要先“钉住”
    出处PMPP 第 2 章Best Practices §9.1 主机与设备间的数据传输
  6. 回到线程的两层结构：为什么要分成 block，而不是一个大平面？因为 block 是一条分界线，线内可以协作，线外互不相干。

  7. 4块与块互不等待，所以同一个程序能在大卡小卡上都跑

    同一个 block 里的线程可以用 __syncthreads() 同步、共用共享内存；不同 block 之间没有执行顺序的保证，彼此独立。硬件可以按任意顺序、以任意并行度调度它们。

    同一个 block 里的线程有两个特权：它们共用一小块很快的存储（共享内存），并且可以用 __syncthreads() 互相等待，意思是“所有人都做到这一步了，再一起往下走”。这让它们能合作完成一件事，比如一起把一块数据搬进共享内存再各自使用（3.3 的分块）。

    不同 block 之间则什么保证都没有：谁先执行、谁后执行、是不是同时执行，都由硬件决定，程序里不能假设。

    这条限制换来的好处是可扩展性。因为 block 互不依赖，硬件可以自由安排：小显卡上同时跑 8 个 block，其余排队；大显卡上同时跑 100 个。程序一个字都不用改，性能自动随硬件增长。这叫 transparent scalability。

    反过来，它也限定了你设计算法的方式：需要线程之间紧密配合的工作，要安排在同一个 block 里；跨 block 的配合，只能通过“先启动一个 kernel 算完，再启动下一个”来实现。

    打个比方像考试分考场：考场里有监考统一口令，考场之间互不相干；考场多就同时开考，考场少就分批考。

    所以同一个 kernel 在 SM 更多的大卡上自动更快（transparent scalability）；也意味着不能写依赖“别的 block 先算完”的逻辑。

串起来

因为 kernel 只描述一个线程的工作，所以关键是线程编号到数据位置的换算；因为数据在两块内存之间搬运很贵，所以要让数据留在 GPU 上；因为 block 之间互相独立，所以同一份程序能在任何大小的 GPU 上运行。
