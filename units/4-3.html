讲解

  1. 1Triton 让你以“块”为单位思考

    Triton 的一个程序实例处理一整块数据，用的是向量化的运算；块内怎么分给线程、怎么合并访存、要不要用共享内存、何时同步，都由编译器决定。

    CUDA 的视角：一个线程。 3.2 讲过，写 CUDA kernel 时你站在一个线程的位置上：我是第几个线程，我负责哪个元素。要性能好，还得自己操心第 3 部分讲的那些事：让相邻线程的访存能合并、决定哪些数据放进共享内存、在合适的地方同步、处理边界上不满一块的情况。

    Triton 的视角：一块数据。 Triton 是嵌在 Python 里的一种写 kernel 的语言。它的一个程序实例负责一整块数据（比如一个 64×64 的小块），代码里操作的是“一块”，写法很像 NumPy：

    @triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(0)                     # 我是第几个程序实例
    offs = pid * BLOCK + tl.arange(0, BLOCK)   # 我负责的这一块的下标
    mask = offs < n                            # 最后一块可能不满
    x = tl.load(x_ptr + offs, mask=mask)       # 读一整块
    y = tl.load(y_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, x + y, mask=mask) # 写一整块

    （这是官方入门教程里向量加法的结构，略去了细节。）

    代码里没有出现“线程”。x + y 是对一整块做加法；这一块里的元素怎样分给各个线程、每个线程读哪几个，是编译器决定的。

    编译器代劳了什么。

    • 把块内的运算分配给一个 block 里的线程。
    • 安排访存的方式，使它们能合并（3.4）。
    • 需要时使用共享内存，插入必要的同步。
    • 对矩阵乘法这样的运算，生成使用 Tensor Core 的指令。
    • 用 mask 统一处理边界，不需要你写单独的分支。

    你仍然要决定的。 数据怎么切成块、块有多大、块与块之间的循环怎么写。也就是算法层面的结构。3.3 的分块矩阵乘法用 Triton 写，仍然是“外层循环遍历 K 方向的块，每次读入两小块、相乘、累加”，只是每一步操作的是块而不是单个元素。

    所以 Triton 没有绕开第 3 部分的知识，而是把其中机械的那一半自动化了。你需要懂的是“为什么要分块、块放在哪一层存储”；不再需要亲手写“第几个线程读第几个地址”。

    和 torch.compile 的关系。 2.5 讲过，Inductor 在 GPU 上生成的就是这样的 Triton 函数。用 TORCH_LOGS=output_code 打印出来的代码，结构和上面这个例子一样：算出这一块的下标，读入几个输入的同一块，做一串运算，写出去。

    打个比方CUDA 像给每个士兵下命令；Triton 像给每个连队下命令，连队内部怎么分工由连长（编译器）安排。

    所以 Triton 代码比 CUDA 短得多，第 3 部分学过的合并访存、分块等优化大多自动完成；你要做的是想清楚数据怎么切块、块多大。

    承接 分块：一次搬一小块进共享内存，大家反复用合并访存：一个 warp 的 32 次读，最好合成一次

  3. 2块多大最好？让它自己试

    最优的块大小、warp 数、流水线级数，取决于矩阵形状和具体的 GPU。Triton 的 autotune 会把几组候选配置都跑一遍，记住最快的那组。

    参数有哪些。 一个 Triton kernel 通常有几个影响性能、不影响结果的参数：

    • 各个方向上的块大小（矩阵乘法有 M、N、K 三个方向）。
    • 每个程序实例用几个 warp。
    • 软件流水线的级数（提前几步预取数据，4.5 的双缓冲就是两级）。

    为什么难算。 块大小牵涉好几个互相矛盾的因素：

    • 块大：每次从显存读进来的数据被复用的次数多，算术强度高（3.3）。
    • 块太大：共享内存和寄存器放不下；一个 SM 上能同时驻留的 block 变少，藏不住访存延迟（3.3 的占用率）。
    • 最合适的折中点取决于具体的 GPU 型号（共享内存多大、有多少寄存器）、矩阵的形状、数据类型。

    这些因素之间的关系没有简单的公式。同一份代码，在 A100 和 H100 上、对 1024×1024 和 128×8192 的矩阵，最优配置可能都不同。

    办法：都试一遍。 给 kernel 加一个装饰器，列出几组候选配置：

    @triton.autotune(
    configs=[
        triton.Config({"BLOCK_M": 128, "BLOCK_N": 64,  "BLOCK_K": 32}, num_warps=4, num_stages=3),
        triton.Config({"BLOCK_M": 64,  "BLOCK_N": 64,  "BLOCK_K": 32}, num_warps=4, num_stages=4),
        ...
    ],
    key=["M", "N", "K"],          # 这几个值变了，就重新搜索
)

    第一次用某种形状调用这个 kernel 时，Triton 把每组配置都编译并运行一遍，记下最快的那组。之后同样形状的调用直接用它。

    代价和注意事项。

    • 第一次调用很慢（要编译和运行所有候选）。测性能时一定要跳过它。
    • key 里的值每出现一种新的组合，都会重新搜索一次。形状变化多的场景，要么限制候选的数量，要么把形状归到几档。
    • 它只在你给的候选里选。候选都不好，选出来的也不好。

    这是性能工程里很常见的一种态度：模型太复杂时，不去推导，直接测量。0.2 的“先量再改”在这里被自动化了。torch.compile 的 max-autotune 模式（2.5）用的是同一个思路。

    打个比方像配眼镜：与其凭经验猜度数，不如几副镜片轮流试一下。

    所以同一份 kernel 能适应不同的形状和显卡；第一次运行慢一点，是它在搜索配置。

  4. 既然 Triton 省事，性能又好，是不是就不用学 CUDA 了？

  5. 3先用 Triton，证明不够再写 CUDA

    Triton 覆盖了大多数融合算子和不少矩阵乘法场景，性能常常接近手写 CUDA；但需要精细控制 warp 级操作、特殊数据布局或最新硬件特性时，仍然要回到 CUDA 或 CUTLASS。

    Triton 擅长的。

    • 融合的逐元素运算和归约（4.2）：这是它最主要的用途，也是 torch.compile 用它来做的事。
    • 规整的、可以按块处理的稠密运算：矩阵乘法及其变体、注意力、归一化。
    • 需要快速试验的新算子：代码短，改起来快，和 PyTorch 在同一个 Python 文件里。

    在这些场景里，Triton 写出来的 kernel 通常能达到手写 CUDA 的八九成甚至持平，代码量却只有几分之一。

    它不擅长的。

    • 需要精细控制每个 warp、每个线程行为的算法。3.5 讲的一些并行模式（比如需要线程之间按特定方式配合的扫描）用“块”的抽象很难表达。
    • 不规整的数据：稀疏矩阵、图、长短不一的序列。
    • 需要特殊的内存布局，或者要用上最新硬件的某个专有特性，而编译器还不支持。
    • 追求最后百分之十几的性能：库的作者（cuBLAS、cuDNN）仍然用更底层的手段。

    一个实际的决策顺序（你的那份文档里把它列为要记住的顺序，这里补上理由）：

    • 先用库。 矩阵乘法、卷积、标准的注意力，库里的实现几乎不可能被你超过。
    • 再用编译器。 自己拼的一串运算，先看 torch.compile 能不能融合好。零代码成本。
    • 然后才是 Triton。 编译器融合不了、或者融合得不好的模式，用 Triton 手写一个。
    • 最后是 CUDA。 只有当 profiler 证明这个 kernel 是瓶颈、Roofline 显示它离硬件上限还远、而 Triton 又表达不了你要的优化时。

    每往下一级，开发和维护的成本都高一个量级，所以要有证据才往下走。

    那为什么第 3 部分花那么多篇幅讲 CUDA。 因为你的目标是读懂和排查，而不只是写。Triton 生成的代码、库里的 kernel、profiler 报告的指标，说的都是 warp、共享内存、访存合并这套语言。不懂底下这一层，就看不懂上面这一层为什么快、为什么慢。

    打个比方像装修：大部分活用成品家具就够了，只有特殊尺寸的角落才值得找木匠定做。

    所以先用 Triton 快速做出够快的版本；只有 profiler 证明它是瓶颈、而且离硬件极限还远时，才值得手写 CUDA。

    承接 先测量，再优化：瓶颈常常不在你以为的地方

串起来

Triton 让你以块为单位写 kernel，块内的线程分配、访存合并、共享内存的使用由编译器负责。块大小等参数用 autotune 搜索。工程上先用 Triton，只有 profiler 证明不够、且离硬件上限还远时，才手写 CUDA。
